# Gradus encryption key-wrapper protocol V1

## Status

Draft protocol specification. It defines the V1 record layouts and cryptographic construction for `core/encryption` key wrappers. **It is not implementation-ready:** the Argon2id profile allowlist and resource caps remain pending the required benchmark on the weakest supported Web/Wasm, Android, iOS, and desktop targets. No client may emit or accept a V1 password wrapper until that table is ratified.

This specification is the companion to [the key-wrapper PRD](prd-encryption-key-wrappers-and-devices.md). It does not define Server persistence or API authentication.

## Scope and conventions

All integers are unsigned big-endian. All byte strings have exactly the stated length. A `magic` is ASCII bytes including the terminating zero byte. Decoders require the exact stated V1 length; there are no extensions or trailing bytes in V1.

Each wrapper is a separately stored opaque value. They are not concatenated into a single cryptographic record. A future Server may transport them in one response, but that outer container is not part of this protocol.

Suite `1` is XChaCha20-Poly1305 with a 32-byte key, a random 24-byte nonce, and its appended 16-byte tag. `ciphertext` therefore means AEAD ciphertext followed by the tag. Every nonce, salt, key, and identifier generated by a client uses the OS CSPRNG.

The AEAD associated data for every wrapper is:

```text
ASCII "gradus/encryption/v1/key-wrapper/aad\0" || header
```

`header` is every record byte before `ciphertext`, including its magic, version, suite, all identities, parameters, salt, and nonce. Thus every cleartext field is authenticated.

## Identities and local encodings

`VaultId` is a random 16-byte public identifier. Its local/transport encoding is:

```text
ASCII "GRDVID\0" || version:u8(1) || vault_id[16]
```

`AccountPublicKey` contains an X25519 public key and its deterministic ID:

```text
account_key_id = SHA-256(
  ASCII "gradus/encryption/v1/account-key-id\0" || public_key[32]
)[0..16]

ASCII "GRDAPUB\0" || version:u8(1) || account_key_id[16] || public_key[32]
```

An account key pair is encoded only for local secure storage:

```text
ASCII "GRDAKEY\0" || version:u8(1) || public_key[32] || private_key[32]
```

A recovery key is 32 random bytes. Its local secure-storage encoding is:

```text
ASCII "GRDRSEC\0" || version:u8(1) || recovery_entropy[32]
```

The existing `GRDVKEY` encoding remains the sole PVK encoding and is never uploaded except inside an encrypted wrapper ciphertext.

## Password PVK wrapper

A password wrapper encrypts the exact 57-byte `GRDVKEY` encoding.

```text
magic[8]              = ASCII "GRDPWVK\0"
version:u8            = 1
suite:u8              = 1
kdf_suite:u8          = 1  # Argon2id v1.3, 32-byte output
vault_id[16]
pvk_key_id[16]
generation:u64
memory_kib:u32
iterations:u32
parallelism:u8
salt[16]
nonce[24]
ciphertext[73]
```

The header is 100 bytes and the complete V1 record is 173 bytes.

The password is the exact UTF-8 encoding of the entered Unicode scalar-value sequence. It is not normalized, trimmed, case-folded, or locale-transformed. The Argon2id output is used directly as the XChaCha20-Poly1305 key. The salt and parameters are inputs to Argon2id and are authenticated in the header.

`generation` starts at `1`. Password replacement creates a new password wrapper with a fresh salt and nonce and an incremented generation. The Server protocol must compare-and-replace this generation atomically with its future authentication-credential/session updates.

## Recovery wrappers

The two recovery wrappers share one `recovery_generation:u64`, starting at `1`. Replacing a recovery key creates both records with a newly generated recovery key, fresh nonces, and the incremented generation; the future Server protocol must atomically replace both.

### Recovery key to PVK

```text
magic[8]              = ASCII "GRDRPVK\0"
version:u8            = 1
suite:u8              = 1
vault_id[16]
pvk_key_id[16]
recovery_generation:u64
nonce[24]
ciphertext[73]
```

The header is 74 bytes and the complete V1 record is 147 bytes. The plaintext is the exact 57-byte `GRDVKEY` encoding. Derive its AEAD key with HKDF-SHA-256:

```text
IKM  = recovery_entropy
salt = empty
info = ASCII "gradus/encryption/v1/recovery-pvk-wrap"
L    = 32
```

### PVK to recovery key

```text
magic[8]              = ASCII "GRDRKEY\0"
version:u8            = 1
suite:u8              = 1
vault_id[16]
pvk_key_id[16]
recovery_generation:u64
nonce[24]
ciphertext[48]
```

The header is 74 bytes and the complete V1 record is 122 bytes. The plaintext is the raw 32-byte recovery entropy. Derive its AEAD key with HKDF-SHA-256 using the PVK secret as IKM, empty salt, and info `gradus/encryption/v1/pvk-recovery-key-wrap`.

## Account private-key wrapper

```text
magic[8]              = ASCII "GRDAKPR\0"
version:u8            = 1
suite:u8              = 1
vault_id[16]
pvk_key_id[16]
account_key_id[16]
account_public_key[32]
nonce[24]
ciphertext[48]
```

The header is 114 bytes and the complete V1 record is 162 bytes. The plaintext is the raw 32-byte X25519 private key. Derive the AEAD key with HKDF-SHA-256 using the PVK secret as IKM, empty salt, and info `gradus/encryption/v1/pvk-account-private-key-wrap`.

On unwrap, an implementation derives the X25519 public key from the plaintext private key, verifies it equals `account_public_key`, and verifies the derived `account_key_id`. It returns no secret if either check fails.

## Recovery mnemonic

A recovery mnemonic represents the raw 32-byte recovery entropy using BIP-39’s 256-bit entropy form, producing exactly 24 words. There is no BIP-39 passphrase.

V1 supports the ten official BIP-39 wordlists: Chinese Simplified, Chinese Traditional, Czech, English, French, Italian, Japanese, Korean, Portuguese, and Spanish. Conversion APIs require a caller-selected `MnemonicLanguage`; V1 does not auto-detect a wordlist. The language is presentation metadata and is not stored in a wrapper: the same recovery entropy can be rendered in another supported language.

BIP-39’s prescribed normalization and word separation rules apply solely to mnemonic conversion. They do not apply to passwords.

## Decode and unwrap rules

1. Decode only exact-length records with a recognized magic, version, and suite. Reject malformed fields before allocating or invoking a KDF.
2. Password-wrapper decoding additionally rejects KDF parameters outside the ratified allowlist or above the explicit V1 resource cap before Argon2id runs. It never lowers stored parameters.
3. Unwrap APIs receive the expected vault ID and PVK key ID. An identity mismatch, incorrect password/recovery key/PVK, altered authenticated field, invalid plaintext encoding, failed public-key verification, or AEAD failure returns only `AuthenticationFailed`.
4. Unsupported record versions/suites and unsupported KDF parameters use their corresponding non-sensitive public error variants. Decode/unwrap errors must not contain secrets, plaintext, record bytes, or cryptographic-library detail.
5. Canonical encoding of a decoded record reproduces its input byte-for-byte.

## Pending KDF benchmark

The V1 password-wrapper format reserves explicit parameters but does not yet assign allowed tuples. The benchmark must run the selected Argon2id implementation and candidate Core/binding path on the weakest supported Web/Wasm, Android, iOS, and desktop hardware.

It must measure cold and warm runs, peak memory/allocation failure, completion time, and battery/foreground behavior. Candidate profiles must meet the PRD’s minimum 128 MiB memory and 4 GiB memory-times-iterations target. The report must publish:

- the finite `(memory_kib, iterations, parallelism)` allowlist;
- the maximum V1 resource cap checked before KDF work;
- the slowest supported-device timings and failure behavior; and
- an explicit decision that every planned platform can accept every allowed profile.

Only then may this document replace this section with the ratified profile table and permit implementation.

## Validation requirements

Publish deterministic vectors containing fixed passwords as UTF-8 bytes, salts, PVK/recovery/account keys, nonces, headers, expected ciphertext records, expected mnemonic output for every supported wordlist, and tampered/malformed cases. Vector files may use JSON for test data presentation, but cryptographic inputs are the exact decoded bytes defined here.

Rust, Dart, Python, and Wasm implementations must consume the same vectors. The implementation test suite must also cover randomized round trips; incorrect identities and secrets; every altered header/ciphertext byte; truncation and trailing bytes; unsupported formats/KDF settings; bounded parsing; and no secrets in errors. Fuzz every decoder and unwrap path for panics and allocation bounds.
